# 简历工作台（Resume-Workbench）：小样本语义架构与实施指南（v2）

> 状态：**已采纳为 v2 架构方向**（2026-11-22），取代此前的 BM25/切词/图谱权重方案。
> 依据：`分析报告/016~019`（匹配实验与深度诊断）、`实验记录/016~017`。
> 实施进度见 `开发与调试流程.md` §9.5。

## 一、 核心架构演进与设计哲学（为什么这么改）

针对"微型个人知识库（总卡片数在 30~100 张以内）"这一核心前提，本架构确立了四项第一性原理：

1. **抛弃传统关键词/索引检索，采用"无索引全量语义扫描"**：
   - 30~50 张精简卡片总计仅约 2,500~4,000 汉字，完全处于大模型的"黄金注意力区间"内（单次扫描成本极低）。
   - 彻底解决 JD 抽象黑话（如"Agent 稳定性保障"）与卡片具体动作（如"四维时间规则约束 + JSON Schema 强校验"）之间的**词汇鸿沟**，实现 **100% 语义理解、零漏召回**。

2. **存储与表达彻底解耦（全要素 6 槽位 vs 7×7 投影模具）**：
   - 卡片入库时不绑定任何简历写法，只存客观完整的 **6 个事实槽位**。写简历时，再将用户的**主策略（定【关键词钩子】）+ 副策略（定【正文叙事逻辑】）+ 深度（L1/L2/L3）** 作为"渲染模具"套在卡片上。

3. **质检前置与两阶段决策（先语义筛选与经历取舍，再局部精写）**：
   - 检索（找得到）与质检（值不值得写）分开处理。先通过全局语义扫描完成"单卡证据质检 + 经历横向 PK 排序 + 篇幅配比"，经人工确认后，再按经历并发加载完整数据进行编译，杜绝跨项目串台和幻觉。

4. **冷热分离与原话溯源**：
   - 原始口述（`Raw`）永远冷存储，仅用于建卡提取、缺口补卡深挖和面试复习溯源，不直接进入常规简历生成管线。

## 二、 数据库结构设计（3 张核心表）

在 SQLite 或本地 JSON 中维护以下三张表即可（去除了冗余的图谱边权重表，大幅降低维护成本）：

### 1. `raw_records`（原始口述冷存储表）

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `raw_id` | TEXT (PK) | 原始记录 ID |
| `exp_id` | TEXT (FK) | 关联的经历 ID |
| `content` | TEXT | 原始口述/笔记全文（绝对真相源，防幻觉底线） |
| `created_at` | DATETIME | 录入时间 |

### 2. `experiences`（经历主干表 —— 简历聚合与排序的基准容器）

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `exp_id` | TEXT (PK) | 经历 ID |
| `category` | TEXT | `internship`（实习）/ `project`（项目）/ `campus`（校园） |
| `title` | TEXT | 经历名称与角色（如 `极简桌面端 AI 待办软件 · 独立产品与开发`） |
| `time_range` | TEXT | 起止时间（如 `2026.08 - 2026.11`） |
| `spine_summary` | TEXT | **全局主干（120~180 字）**：按时间线说清"背景目标 → 核心演进阶段 → 最终成果" |

### 3. `story_cards`（全要素决策卡片表 —— 核心知识资产）

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `card_id` | TEXT (PK) | 卡片 ID |
| `exp_id` | TEXT (FK) | 归属经历 ID |
| `step_order` | INT | 在该经历中的时间/因果推进序号（1, 2, 3...），保证叙事连贯 |
| `toc_title` | TEXT | **短标题（20 字内）**：概括做了什么决策/解决了什么问题 |
| `quality_grade` | TEXT | **静态含金量评级（入库即生成）**：`S`（痛点+动作+量化结果齐全）/ `A`（有扎实动作但无量化数字）/ `B`（仅工具罗列或模块描述，弱证据） |
| `slot_stage` | TEXT | **槽位 1（阶段）**：0-1 架构期 / 核心开发期 / 调优迭代期 *(支撑策略 6)* |
| `slot_module` | TEXT | **槽位 2（模块）**：所属业务域或功能模块名 *(支撑策略 1)* |
| `slot_problem` | TEXT | **槽位 3（痛点与判断）**：核心卡点、方案权衡与决策依据 *(支撑策略 3)* |
| `slot_workflow` | TEXT | **槽位 4（流程步骤）**：输入 → 核心处理动作 → 交付输出 *(支撑策略 2)* |
| `slot_tech_link` | TEXT | **槽位 5（技术链路）**：技术栈、模型、API 及数据/调用流转关系 *(支撑策略 5)* |
| `slot_outcome` | TEXT | **槽位 6（成果与能力）**：客观结果/量化指标 + 体现的核心能力 *(支撑策略 4、7)* |
| `raw_quote` | TEXT | 从 `Raw` 中一字不差截取的 1~3 句原话（供面试前核对，不进生成上下文） |
| `is_verified` | BOOLEAN | **人工确认开关**：仅 `true` 的卡片允许进入扫描与生成管线 |

## 三、 四阶段端到端工作流（系统运行逻辑）

### 阶段 1：知识入库与静态质检（离线沉淀，一次建卡永久复用）

1. **口述录入**：用户在某段经历下输入口述文本，存入 `raw_records`。
2. **LLM 切分建卡（遵循"独立闭环原则"）**：
   - 只要出现**新的子问题/卡点**、**新阶段**或**独立技术决策**，就切分为一张新卡（避免全合成 1 张大卡，每段核心经历目标产出 **5~8 张卡**）；同一决策的补充解释合并在同一张卡内。
   - 严禁脑补未提及的数据或技术，缺失信息统一填 `"未提及"`。
3. **自动静态质检（规则脚本后处理）**：
   - 代码自动检查卡片强槽位（`slot_problem`、`slot_workflow`、`slot_outcome`）的完整度与数字/主导词特征，自动打上 `S` / `A` / `B` 静态质量评级。
4. **人工确认入库**：前端展示提取出的卡片与原话锚点，用户核对无误后点击【确认入库】（`is_verified = true`）。

### 阶段 2：无索引全量语义扫描与经历取舍（JD 进来后的核心决策）

面对新 JD 时，**不提取关键词、不跑 BM25**，直接执行一次全局语义扫描：

1. **组装轻量扫描包（约 3,000~4,000 Tokens）**：
   - 输入：`完整 JD` + `所有经历的 spine_summary` + `全库已确认卡片的精简视图（仅含 card_id、exp_id、step_order、quality_grade、以及 3 个强槽位 problem/workflow/outcome）`。
   - *注：`B` 级弱卡默认标记为【降级兜底池】，仅在 `S/A` 级卡数量不足时启用。*
2. **LLM 全局扫描与仲裁（输出结构化决策报告）**：
   - **语义对齐与匹配理由**：跨字面黑话匹配 JD 诉求与卡片强槽位，为每张入选卡片生成一句"匹配理由（JD 要求 X ↔ 卡片做法 Y）"。
   - **证据可写度质检**：剔除"仅表面沾边但缺乏行动支撑"的伪匹配卡片。
   - **经历级横向 PK 排序与篇幅分配**：按每段经历命中的高质量卡片数量与契合度，对所有经历进行排序，给出建议（例如：`经历 A` 排第 1，主推详写 3~4 条；`经历 B` 排第 2，补充略写 1~2 条；`经历 C` 建议本次舍弃）。
   - **缺口预警（Gap Detection）**：如果某段主推经历高度契合 JD，但明显缺少 JD 看重的某个维度（如"异常兜底"或"数据复盘"），直接输出一条缺口提示。

### 阶段 3：选点确认台 & 动态补卡（Human-in-the-Loop）

前端展示扫描结果，用户在真正生成简历前拥有 100% 掌控权：

1. **可视化选点与策略配置**：
   - 按推荐排序展示各段经历，大模型推荐的卡片已自动勾选 `[x]` 并附带"匹配理由"，全库其他卡片也在列表中供用户随时手动补勾或取消。
   - 用户为每段经历确认（或微调）渲染策略：**主策略（定【关键词钩子】）+ 副策略（定【正文叙事】）+ 深度（L1 宏观 / L2 方案 / L3 细节）**。
2. **动态补卡（Gap Filling）**：
   - 针对阶段 2 提示的缺口（或用户自己想补充的点），点击【+ 针对此问题补卡】。
   - 大模型带着该问题回溯检索该经历对应的 `raw_records` 原文（若原文未提及，则向用户发起 1 个简短追问），生成一张新的 6 槽位卡片，用户确认后直接加入本次生成队列并存入知识库。

### 阶段 4：按经历并发局部编译（高保真、防串台）

点击【生成简历】后，系统按经历排序顺序，**为每段入选经历发起独立的 LLM 编译请求**（每段经历一个干净上下文，绝不混杂其他经历信息）：

1. **局部加载**：仅传入当前经历的 `spine_summary` + **用户勾选的那 2~4 张卡片的完整 6 槽位数据**（严格按 `step_order` 升序排列，保证时间线与因果连贯）。
2. **双维策略模具渲染**：
   - **主策略**控制每条 Bullet 开头的【关键词钩子】提炼角度（从 7 种模式中选一）。
   - **副策略**控制正文的逻辑展开顺序（从 7 种模式中选一），受控于指定的**深度（L1/L2/L3）**。
   - 输出的每条简历 Bullet 绑定对应的 `card_id`，前端支持点击该句简历直接弹窗查看 `raw_quote` 原始口述，方便面试前随时核对细节、准备追问话术。

### 模板 B：全局语义扫描与经历取舍 Prompt（阶段 2 核心）

```markdown
# Role
你是一个资深技术/产品招聘专家与简历策略主编。请根据【目标 JD】，对候选人知识库中的【全量经历与决策卡片】进行深度语义扫描、证据质量质检与经历级取舍排序。

# Core Rules
1. **跨语义深度匹配（拒绝机械找词）**：不要局限于字面关键词重合，重点考察卡片的 `slot_problem`（痛点决策）、`slot_workflow`（具体动作）和 `slot_outcome`（实际结果）是否能实质性印证 JD 的能力要求。
2. **证据质量一票否决**：优先选用 `quality_grade` 为 `S` 或 `A` 的卡片。若卡片缺乏具体行动与结果支撑，即便词面沾边也不得选为主力 Bullet。
3. **叙事连贯性保护**：同一段经历若选中多张卡片，注意保留能体现"启动/架构 → 核心攻坚 → 迭代/结果"完整逻辑链的卡片（关注 `step_order`），避免只挑孤立的边缘细节。
4. **客观缺口诊断**：若某段核心经历非常值得写，但针对 JD 最看重的 1-2 项核心要求目前没有对应卡片，请在 `gaps` 中明确指出，以便触发后续补卡。

# Output Schema (严格输出合法 JSON)
{
  "jd_analysis": {
    "core_demands": ["提炼JD最核心的3-5项能力/业务诉求"],
    "recommended_strategy": {
      "main_strategy": "推荐主策略(1-7编号及名称，定关键词钩子)",
      "sub_strategy": "推荐副策略(1-7编号及名称，定正文展开)",
      "depth": "L1 | L2 | L3",
      "reason": "一句话说明为什么推荐该策略组合"

  },
  "experience_rankings": [
    {
      "exp_id": "经历ID",
      "priority_rank": 1,
      "decision": "主推详写(建议3-4条) | 补充略写(建议1-2条) | 建议舍弃",
      "selected_cards": [
        {
          "card_id": "卡片ID",
          "step_order": 1,
          "match_reason": "一句话说明：该卡片的【具体动作/决策】如何印证 JD 的【某项具体要求】"
        }
      ],
      "gaps": ["若无缺口则为空数组；若有缺口，描述建议从原话深挖补充的方向，如：建议补充关于大模型输出异常兜底机制的决策细节"]
    }
  ]
}
```

### 模板 C：双维策略局部编译 Prompt（阶段 4 核心）

```markdown
# Role
你是一个顶尖的简历撰写专家。请严格基于提供的【单段经历主干】和【已选决策卡片（6槽位事实）】，按照指定的【双维表达策略】将其编译为专业、克制、经得起面试深挖的简历描述（Bullets）。

# Constraints
1. **绝对忠于输入事实**：严禁编造卡片中未出现的数字、工具或业务结果。
2. **逻辑连贯**：传入的卡片已按 `step_order` 排序，输出的多条 Bullet 之间必须体现清晰的时间演进或逻辑递进关系。
3. **双维策略严格执行**：
   - 每条 Bullet 必须采用 `【关键词钩子】正文内容` 的格式。
   - **【关键词钩子】**必须严格遵循【主策略：{main_strategy}】的视角进行提炼。
   - **正文内容**必须严格遵循【副策略：{sub_strategy}】的叙事逻辑进行组织，并严格控制信息颗粒度为【深度：{depth}】（L1侧重业务价值与目标；L2侧重方案设计与处理流程；L3侧重具体技术组件、参数规则与底层细节）。

# 7 种策略定义参考
1. 功能模块型：突出业务/功能模块名称与职责闭环。
2. 工作流程型：严格按"输入 → 核心处理步骤 → 交付输出"展开。
3. 问题解决型：按"业务/技术卡点 → 方案权衡判断 → 落地解法与结果"展开。
4. 业务成果型：结论先行，先抛核心指标/收益，再拆解达成路径。
5. 技术链路型：突出技术组件选型、系统连接与数据流转关系。
6. 项目阶段型：突出阶段里程碑（如0-1搭建/架构重构）与时间演进。
7. 核心能力型：突出与岗位匹配的抽象方法论/核心能力，并用具体动作佐证。

# Output Schema (严格输出合法 JSON)
{
  "exp_id": "经历ID",

    {
      "card_id": "对应的卡片ID（用于前端绑定原话溯源）",
      "hook": "关键词钩子（不含括号，4-10字）",
      "content": "正文内容（紧凑有力，45-75字为宜）"
    }
  ]
}
```

## 五、 实施路线图（按此顺序推进，最快跑通）

1. **Step 1（数据层清理与静态质检）**：
   - 调整 `story_cards` 表结构，加入 `quality_grade` 字段，删除旧的 `card_node_links` 复杂权重逻辑。
   - 写一个 20 行的后处理函数，对现有 31 张卡自动跑一遍强槽位完整度检查，标出 `S / A / B` 等级。
2. **Step 2（替换检索层为"全量语义扫描"）**：
   - 删掉原来的切词/BM25 匹配代码，接入 **模板 B（全局语义扫描 Prompt）**，输入 JD + 全库卡片强槽位精简 JSON，验证其输出经历排序和 `match_reason` 的准确度。
3. **Step 3（对接确认台与局部编译）**：
   - 前端将模板 B 返回的推荐卡片默认勾选并展示 `match_reason`，接入策略选择器（主策略 + 副策略 + 深度）。
   - 确认后并发调用 **模板 C（双维策略局部编译 Prompt）**，渲染最终简历，并实现点击句子弹窗查看 `raw_quote` 原话。
4. **Step 4（补齐动态补卡闭环）**：
   - 在确认台读取 `gaps` 字段，点击补卡按钮时，带着缺口问题去查询对应 `raw_records` 原文并复用 **模板 A** 生成新卡片。
